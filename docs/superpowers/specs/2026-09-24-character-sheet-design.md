# 角色卡骨幹設計 — Phase 4 的第一塊

> 定案日期：2026-09-24
> 影響範圍：`app/`（新增角色卡層）。資料管線、`db/schema.sql`、`tools/` 完全不動。
> 前置狀態：規則書閱讀介面與勘誤編輯皆已完成

## Phase 4 的拆解

`docs/PLAN.md` 的 Phase 4 是四個子系統，一份規格裝不下：

```
① 角色卡骨幹 ──┬─► ② 建卡精靈
（模型+計算+存檔）├─► ③ 施法者分支
                └─► ④ 跑團模式
```

②③④ 都要先有「一張角色卡」才有東西可操作，所以從 ① 開始。
本文件只談 ①，其餘各自會有自己的規格。

① 另有一個現成的驗收基準：**「法師範例」那張算好的角色卡**。
`tools/validate.py` 已經拿它回歸驗證過 `rules.py` 的十六項衍生數值，
`rules.rs` 移植完可以用同一組數字，兩份實作分歧時測試會抓到。

## 一、這個專案第一次有「使用者資料」

在此之前所有狀態都是唯讀的建置產物（`dist/d100.db`）或 git 裡的文字檔
（`data/errata`）。角色卡兩者都不是 —— 它屬於玩家、在玩家的機器上、
不進 repo。

因此角色卡存在**使用者資料夾**（`AppData` 之類，由 Tauri 解析），
一張卡一個 JSON。這也是本專案第一個打包版就完整可用的寫入功能。

## 二、資料模型：能算的一律不存

**原始輸入**（存進 JSON）：

| 欄位 | 說明 |
|---|---|
| `name` | 角色名 |
| `starting_cp` | DM 給的起始 CP |
| `attributes` | 九大屬性的數值 |
| `race_id` | 種族。CP 調整由種族資料帶出 |
| `feats[]` | `{feat_id, level, track}`，track 為 `melee` / `spell` / `none` |
| `bonus_rolls` | 獎勵 HP/SP 的**擲骰結果**，兩軌各一組 |
| `manual_hp` / `manual_sp` | 專長與詞綴提供的 HP/SP |
| `extra_hp` / `extra_sp` | 以 CP 加購後的目標值 |
| `adjustments` | 每項衍生值的 `{delta, note}` |

**衍生值**（永不存檔，每次重算）：屬性調整值、六大技能、五抗性、
三特殊、基礎 HP/SP、CP 收支、獎勵骰數階級。

**能算的一律不存。** 存了就會跟公式不同步 —— 這跟「`dist/d100.db` 是
建置產物、刪掉可以重建」是同一條原則。

### 為什麼獎勵 HP/SP 是原始輸入

規則書的獎勵是**骰子**而非固定值（達 10CP 送 `1d8HP＋1d4SP`，
達 30CP 送 `2d8HP＋2d4SP`⋯）。骰數階級算得出來，骰出來的點數算不出來。
因此程式的職責是告訴玩家「你現在該擲 3d8＋3d4」，結果由玩家填回來。

同理，基礎 HP/SP 公式裡的「專長表之技能＋魔法物品之詞綴」是效果敘述
裡的自由文字，程式讀不出來，手填。

### 進戰軌與法術軌由玩家逐條標記

規則書沒有定義哪些專長算「進戰相關」、哪些算「法術相關」，而專長表的
分類欄（六大技能判定）與這兩軌對不起來。程式無法從資料推出來。

作法是加入專長時由玩家標記。不猜測、可追溯，代價是多一個手動步驟。
這一項已列入 [規則裁示紀錄](../../規則裁示紀錄.md) 第 12 項待確認。

### 修正欄：公式不動，差額並存

實際跑團一定會有公式沒涵蓋的加值（裝備、buff、DM 裁定）。作法不是把
衍生值覆寫成任意數字，而是每項旁邊可以填一個 `修正 +N` 與註記。

顯示成 **`公式值 ＋ 修正 ＝ 顯示值`**，三個數字都看得到。

這與專案處理勘誤的方式一致：原值保留、修正與理由並存。直接覆寫會遺失
「本來應該是多少」，屬性改了之後也不知道那個覆寫還算不算數。

## 三、計算核心

把 `tools/rules.py` 尚未移植的部分補進 `src-tauri/src/rules.rs`：

- `attribute_modifier`：13 為 0，每 ±2 一階
- `effective`：屬性值＋其調整值
- `skill_value`：六大技能。**知識 `(INT＋WIS)×1.5` 無條件捨去** ——
  2026-09-20 的裁示，Patch 1.1 的「≥0.5 進位」只管擲骰結果
- `resist_value`：五抗性
- `special_value`：三特殊，不計調整值
- `attribute_cp_adjustment`：調整值總和對起始 CP 的增減
- `bonus_dice_steps`：依投入 CP 算獎勵骰數階級
- `extra_hp_cp_cost`：額外 HP/SP 的累進換匯
- `base_hp` / `base_sp`：`CON＋CON調整值＋獎勵＋手填`

### 回歸測試讀與 validate.py 同一個檔案

`tools/validate.py` 是在執行時讀 `data/raw/法師範例.tsv`，不是寫死數字。
`rules.rs` 的測試**讀同一個檔案**，於是兩份實作被釘在同一個真相上：
上游試算表改了，兩邊都會發現。

這與既有做法一致 —— `db` 的測試也是跑在真正的 `dist/d100.db` 上。

## 四、存檔

一張卡一個 JSON，放使用者資料夾的 `characters/<id>.json`。

**JSON 就是模型本身**，所以匯出匯入幾乎是附贈的：匯出是複製檔案，
匯入是讀進來、換一個新 id、存起來。

帶 `schema_version`。模型日後一定會改（③ 要加施法者欄位、④ 要加狀態），
沒有版本欄就沒辦法遷移。讀到不認得的版本時明白拒絕並說明，不要猜。

## 五、角色卡頁

章節列新增「角色卡」。左側是卡片清單（新增／複製／刪除／匯入匯出），
右側是單張卡。

- 原始輸入是表單
- 衍生值即時重算，顯示 `公式值 ＋ 修正 ＝ 顯示值`
- 專長用既有的挑選器（`feat_difficulties` 已經有了）選，選完顯示該條的
  CP 成本並要求標軌別

**軟性警告、不擋**：前置未滿足、CP 超支、獎勵骰數與已填的擲骰結果對不上。
與 `PLAN.md` 的「所有規則衝突以警告呈現，可覆寫」一致。

刪除角色卡要確認 —— 那是使用者自己產生的資料，刪掉沒得復原。

## 六、程式結構

```
src-tauri/src/
  rules.rs          擴充：屬性、技能、抗性、特殊、HP/SP、CP 收支
  sheet/mod.rs      模型與衍生值計算
  sheet/store.rs    JSON 讀寫（使用者資料夾）
src/
  chapters/SheetChapter.tsx   清單與單張卡
  components/SheetForm.tsx    原始輸入
  components/DerivedPanel.tsx 衍生值與修正
```

新增指令：`list_sheets`、`load_sheet`、`save_sheet`、`delete_sheet`、
`derive_sheet`、`import_sheet`、`export_sheet`。

`derive_sheet` 是純計算、不碰檔案 —— 表單每改一個字就重算一次，
不該有 I/O。

## 七、測試

- `rules.rs`：拿 `data/raw/法師範例.tsv` 回歸十六項衍生數值
- `sheet/mod.rs`：CP 收支、獎勵骰數階級、額外 HP/SP 換匯、修正欄的加總
- `sheet/store.rs`：讀寫與 `schema_version` 的拒絕行為，跑在暫存目錄

前端沿用既有做法：型別由 `tsc` 把關，行為靠實際操作驗證。
