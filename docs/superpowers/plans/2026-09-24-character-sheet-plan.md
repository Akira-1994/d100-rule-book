## 起點與原則

**起點**：20 個指令、49 個 Rust 測試、零警告。`rules.rs` 目前只有 CP 那一段。

**每個階段結束時應用必須可跑。** 與前兩次改版相同。

**不得在測試中寫入使用者資料夾。** 與「不得寫入 `data/errata`」同一條紀律：
存檔測試一律在暫存目錄進行，不碰真實的角色卡。

**每個任務結束時跑**：

```bash
cd app && npm run build && cd src-tauri && cargo test --lib
```

## 階段 1 — 計算核心

做完沒有畫面變化，但公式全部就位且被法師範例釘住。

### 1.1 讀取法師範例的測試工具

`tools/validate.py` 在執行時讀 `data/raw/法師範例.tsv`。Rust 測試要讀同一個
檔案，才能讓兩份實作釘在同一個真相上。

- `rules.rs` 的測試模組新增讀取函式：解析 TSV，取出九大屬性與表上算好的
  十六項衍生數值
- 檔案找不到時明白失敗並說明要跑 `extract.py`，與 `db::test_conn` 的做法一致

**驗收**：測試能讀出 9 個屬性與 16 項期望值，數量不對就失敗。

### 1.2 屬性與衍生判定

移植 `attribute_modifier`、`effective`、`skill_value`、`resist_value`、
`special_value`。

**知識用 `int()` 截斷**（`(INT＋WIS)×1.5` 無條件捨去）—— 2026-09-20 的裁示，
Patch 1.1 的「≥0.5 進位」只管擲骰結果。範例卡的 `(24+19)×1.5 = 64.5 → 64`
就是這一條的證據。

**驗收**：十六項全部與範例卡相符。這是整個階段的核心驗收。

### 1.3 CP 與 HP/SP

移植 `attribute_cp_adjustment`、`bonus_dice_steps`、`extra_hp_cp_cost`，
新增 `base_hp` / `base_sp`。

**驗收**：
- 調整值總和 10 時 CP 增減為 0；超過每點扣 10、低於每點加 10
- 骰數階級在七個門檻（10/30/70/150/300/620/1020）各跳一階，9 CP 時為 0
- 額外 HP 換匯：基礎 30 時，31–60 為 1:1、61–90 為 2:1（原文的例子）

## 階段 2 — 模型與存檔

### 2.1 `sheet/mod.rs`：模型與衍生值

設計文件第二節那張表的結構，加上 `derive()`：吃一張卡回傳所有衍生值。

- `derive()` **純計算、不碰檔案也不碰資料庫**⁽¹⁾
- 修正欄的加總在這裡做：`顯示值 = 公式值 + 修正`，三個數字都要回傳
- 兩軌的 CP 投資依 `feats[].track` 加總

⁽¹⁾ 例外：種族的 CP 調整與專長的難度要查資料庫。那些是**輸入**而非計算，
由呼叫端先查好傳進來，`derive()` 本身仍是純函式 —— 這樣才測得動。

**驗收**：
- 一張手寫的測試卡，驗 CP 收支、兩軌投資、修正欄加總
- `derive()` 不接受 `Connection` 參數（純函式，以簽章保證）

### 2.2 `sheet/store.rs`：JSON 讀寫

使用者資料夾的 `characters/<id>.json`。

- `schema_version` 不認得時明白拒絕並說明，不要猜
- 刪除是真的刪檔案，呼叫端負責確認
- 匯入＝讀進來、換新 id、存起來

**驗收**（全部在暫存目錄）：
- 存了再讀回來，內容一致
- 讀到未來版本的 `schema_version` 時回報錯誤而非 panic 或靜默忽略
- 匯入同一個檔案兩次會得到兩張不同 id 的卡

### 2.3 指令

`list_sheets`、`load_sheet`、`save_sheet`、`delete_sheet`、`derive_sheet`、
`import_sheet`、`export_sheet`。

**驗收**：指令數由 20 增為 27，`api.ts` 與 `lib.rs` 兩邊名稱對應。

## 階段 3 — 角色卡頁

### 3.1 章節與清單

`db/toc.rs` 新增「角色卡」章節。左側清單（新增／複製／刪除／匯入匯出）。

**刪除要確認** —— 那是使用者自己產生的資料，刪掉沒得復原。

### 3.2 `SheetForm.tsx`：原始輸入

九屬性、種族、起始 CP、獎勵擲骰結果、手填 HP/SP、額外 HP/SP。

### 3.3 專長清單與軌別

用既有的 `feat_difficulties` 挑選器選專長，選完設等級與軌別。
顯示每條的 CP 成本。

### 3.4 `DerivedPanel.tsx`：衍生值與修正

每項顯示 `公式值 ＋ 修正 ＝ 顯示值`，修正可就地編輯並加註記。

### 3.5 軟性警告

前置未滿足、CP 超支、獎勵骰數與已填擲骰結果對不上。
**一律只提示、不擋存檔。**

**階段 3 手動驗收**（端到端）：

1. 新增一張卡，填入法師範例的九個屬性
2. 六大技能、五抗性、三特殊應與範例卡的十六項完全相同
3. 加一條專長、設等級與軌別，CP 餘額跟著變
4. 在「感知」加一個修正 +5 並註記，顯示值變成 `61 ＋ 5 ＝ 66`
5. 關掉應用重開，那張卡還在且數值一致
6. 匯出、刪除、再匯入，內容一致但 id 不同

## 風險與對策

1. **測試污染使用者資料夾**。所有存檔測試用暫存目錄；手動驗收產生的卡
   驗完自己刪掉。
2. **模型之後一定會改**（③ 加施法者欄位、④ 加狀態）。`schema_version`
   從第一天就有，且讀到不認得的版本時明白拒絕。
3. **兩軌判定尚未經作者確認**（規則裁示紀錄第 12 項）。若日後改為可由
   分類推出，`feats[].track` 會變成可選而非必填 —— 影響的是輸入介面，
   不是計算核心。

## 明確不做

- 建卡精靈、施法者欄位、跑團模式、魔法物品配置介面
- 硬性驗證
- 不碰 `data/`、`db/schema.sql`、`tools/`
