## 規則骨架（Phase 4 數學基礎）

- 九大屬性：STR / DEX / SKI / CON / RES / INT / WIS / CHA / SPI，4D6 擲骰
- 屬性調整值：13 為 0，每 ±2 一階（7→-3 … 19→+3）；調整值總和超過 10 每點扣 10 CP，低於 10 每點加 10 CP
- 六大技能判定
  - 戰鬥 = DEX + SKI + STR
  - 運動 = DEX + SKI + CON
  - 操作 = INT + SKI + WIS
  - 感知 = INT + RES + SPI
  - 知識 = (INT + WIS) × 1.5
  - 交涉 = CHA + WIS + SPI
- 五抗性：抗毒素 = RES+CON、抗控制 = RES+WIS、抗轉化 = RES×2、抗噴吐 = RES+DEX、抗魔法 = RES+INT
- 三特殊（不計調整值）：強韌 = CON×5、精神 = RES×5、靈魂 = SPI×5
- CP 消耗：`2^等級 × 難度`；等級 0 亦需付費（免除該技能判定 20% 減值）
- 獎勵 HP/SP 門檻：10 / 30 / 70 / 150 / 300 / 620 / 1020 CP，進戰軌與法術軌可累算
- 額外 HP/SP 轉換：基礎值每多一倍，換匯率 +1（1x–2x 為 1:1，2x–3x 為 2:1，依此類推）
- 施法者等級 = 本身環數 × 3 + 變動值
- 法術位 = 環數 × 2 + 主屬性調整值 + 魔法物品變動值 + 技能變動值
- 施法檢定 = 主屬性 + 10×(總施法者等級/3) − 連續施法懲罰 − 本次環數×10
- 擲骰結果小數 ≥ 0.5 一律進位（Patch 1.1）

## 已知資料問題（Phase 2 處理）

以 `tools/verify_extract.py` 確認擷取無損後，重新稽核 data/raw 得到的實際清單：

1. 分類欄用語不一致：`感知/知識` 與 `知識/感知` 並存，另有 `戰鬥/運動`、
   `操作/知識`、`知識/交涉`、`知識、\n感知或交涉` 等自由寫法
2. 難度欄非純數值：基本專長的〈知識〉〈語言〉為 `1or2`；
   高級專長〈大師之觸- 金繼〉難度整格空白
3. 高級專長〈星辰大樂章(第五幕)-〉名稱在破折號後截斷，且**整格缺少效果敘述**
4. 高級專長〈大師之觸- 金繼〉是〈大師之觸（Masterpiece）〉的子項，
   以空白分類／難度表示繼承，但表格結構本身沒有父子關係的表達方式
5. 種族表的 CP 調整混用半形 `-30` 與全形 `－25`，另有非數值的 `劇情取得`；
   種族名稱含換行（`神魔裔\n（潘神之子）`）與前導空白（` 原初-星之幼體`）
6. 詞綴的「所需加值兌換」是多階清單（`2、4、6` 代表三個階級），
   其中一筆為條件式：`3（鎧甲、盾牌）\n2（武器）`
7. 前置條件為自由文字，混用「施法環數達四環以上」「綁定血脈:神魔裔」
   「跑步二級」「神語1級」等多種格式
8. 全表零公式（狩獵任務除外），所有衍生數值靠人工計算

## Phase 1 — 資料固化與變更追蹤

**目標**：xlsx 更新時，`git diff` 能直接指出哪一條的哪個欄位改了。

- [ ] `data/source/D100專長表.xlsx` 納管，記錄 SHA-256
- [ ] `tools/extract.py`：純機械式轉換（零判斷），每張表 → `data/raw/<NN>_<表名>.tsv`
      規則：None → 空字串、換行 → `\n`、去除尾端空欄、去除尾端空列
      驗收：同一份 xlsx 重跑必須逐 byte 相同
- [ ] `data/raw/manifest.json`：每張表的列數／欄數／內容雜湊
- [ ] `tools/diff_report.py`：比對兩版 manifest + TSV，輸出中文變更報告
- [ ] pre-commit hook：xlsx 變更時強制重跑 extract，避免 raw 與 xlsx 不同步

**原則**：Phase 1 不做任何清理。raw 層只負責忠實映射，清理留到 Phase 2，
才能區分「上游真的改了」與「我們的解析邏輯改了」。

### Tier C 的做法：版面宣告

職業表是排版而非資料 —— 同一張工作表上並排數張卡片、沒有可靠表頭、
欄位位置各表不同（術士是 C1/C13/C25，牧師領域是 C1/C10/C19，
武僧是 C1/C9/C17）。硬寫推斷邏輯會既脆弱又難維護。

改採「人宣告區塊、程式機械切割」：每張表對應一份
`data/layout/<工作表>.yaml`，由人看過一次後寫明區塊起始欄、欄位順序、
以及少數例外（哪些標題其實是版面橫幅、哪個區塊其實是另一個職業）。
解析器只負責照著切，不做任何猜測。

實際踩到並已處理的版面變體：

1. **一張表並排多個不同職業** —— 特殊職業1 的三個區塊分別是奈瑟瑞爾奧術師、
   賢者、聖騎士，各自都有同名的「基本前置專長」「進階專長」章節，
   因此區塊可逐一指定 `class_name`
2. **版面橫幅不是章節** —— 牧師領域 C10 與 C19 的最上方都寫「神祇領域」，
   真正的領域從下一組開始。以 `banner_sections` 宣告後改收進 `rule_text`
3. **一組連續標題裡混著橫幅、真章節與說明** —— 逐列判斷而非整組取一個名稱
4. **章節名把條件折到第二行** —— 只用第一行判斷是否為標題
5. **難度欄把前置折到第二行**（`難度4\n（前置法術瞬唱）`）—— 拆開後併入前置
6. **無難度的被動特性** —— 武僧的「不殺」、聖騎士的「至善之魂」、
   如來神掌的九式，都是名稱加一段敘述、不能用 CP 購買也無法升級。
   放進 `feat` 會讓建卡介面誤以為可以學，因此獨立成 `class_trait` 表
7. **名稱裡藏零寬空白** —— 「​迷惑學院」與「​劍宗」名稱前各有一個 U+200B，
   在儲存格裡看不見卻會讓 id 產生失敗，已在 `clean_name` 統一清除

成果：96 個流派、361 個職業專長、27 個被動特性，解析問題全部是原始資料
本身的缺口（缺效果、缺分類），沒有一項是解析失敗。

### Tier C 第二批：散文與對照表

職業表之外還有兩類東西，同樣以版面宣告處理：

**散文規則**（`data/layout/prose/`）—— 創角流程、戰鬥流程、世界觀、
大陸簡史、FATE 特規、Patch note、施法者創角須知。版面是「標題欄 + 內容欄」，
戰鬥流程有兩層（大步驟底下再分一般／自由／即時動作）。三種版面變體：

1. 標題與內容在不同欄（多數表）
2. 兩層巢狀，且第二層的標題欄就是第一層的內容欄（戰鬥流程）——
   若不特別處理，大步驟的說明文字會被誤當成子項名稱
3. 標題與內容上下交錯、又擠在同一欄（施法者創角須知）——
   長度與標點都區分不開（「奧術知識（知識）難度2」比
   「法師應先決技能及應注意事項」還短），因此改由 `mode: explicit` 逐段宣告列號

**小型對照表**（`data/layout/tables/`）—— 31 張，269 列。欄位各不相同，
一張張建資料表並不划算，統一收進 `ref_table` / `ref_row`（欄名與儲存格
各存成 JSON 陣列）。其中「魔法物品價格表」一張工作表就拼了 12 張小表，
「詞綴條數量分布」則是橫著排的，需要轉置。

另外兩個專屬模型：Warlock 的 58 條**魔能祈喚**（不是可升級的技能，
消耗的是祈喚欄位而非 CP），以及混沌石用的 685 筆**詞綴分布**
（部位 × 加值等級 → 可出現的詞綴）。

**Schema 草案**

實作見 [db/schema.sql](../db/schema.sql)。已建立的表：

```
feat / feat_category / feat_tag / feat_prereq
race / race_attr_modifier
affix / affix_slot / affix_rank

rule_text          -- 表頭之前的前言段落

```

Tier C 另外建立：`class_path`（學派／血脈／領域／結社統一模型）、`class_trait`、
`invocation`、`ref_table` / `ref_row`（31 張小型對照表）、`affix_distribution`，
以及 `equipment_slot` / `affix_slot_mapping`（詞綴部位 → 角色卡欄位）。

**技術決定**

資料庫唯讀。編輯功能是改 `data/errata` 的 YAML 再重建資料庫，而不是直接寫
`.db` —— 直接改會讓修改失去可追溯性，也違背「SQLite 是建置產物」這個前提。

後端邏輯有 `cargo test --lib` 的測試，直接跑在真正的 `dist/d100.db` 上。
造假資料在這裡沒有意義，我們要驗的正是「查詢能不能正確對付這份資料的形狀」。

章節與頁籤的定義寫死在 `db/toc.rs`，不進資料庫 —— 哪一章放哪些工作表是編輯
判斷，不是試算表的內容。這條界線與「`data/raw` 不做語意判斷」是同一個道理。

CP 成本表與勘誤不放在專長卡上：前者是全書通則而非每條專長各自的性質，
後者是給規則書作者對帳用的資訊。兩者各自有獨立的去處（階段 3 的試算工具、
階段 2 的附錄章節）。

## 風險

1. **Tier C 職業表是排版而非資料**。硬寫解析器脆弱且痛苦。建議一次性人工轉成 YAML（9 張表），之後由 App 維護不再回頭解析。代價：Phase 1 的 diff 對這幾張表只能提示「這區有變動」，細節仍需人眼確認。
2. **前置條件文字化**是 Phase 4 自動驗證的瓶頸。採漸進策略：`raw_text` 與結構化欄位並存，解析率逐步提升。
3. **Phase 1 的 diff 品質決定後三個 Phase 的成本**。不應為趕進度跳過 manifest 與可重現性設計。
