# D100 規則書應用

Tauri 2 + React 19 + TypeScript。後端以 Rust 讀 `dist/d100.db`，前端只負責呈現。

## 開發

```bash
cd app
npm install
npm run sync-db      # 把 dist/d100.db 複製進 src-tauri/resources
npm run tauri dev
```

`sync-db` 是必要步驟：Tauri 在建置時會檢查 `bundle.resources` 列出的檔案存在，
而資料庫是 `tools/build_db.py` 的產物、不進 git。規則書內容更新後要重跑：

```bash
python ../tools/build_db.py && npm run sync-db
```

## 打包

```bash
npm run sync-db && npm run tauri build
```

資料庫會一起打包進安裝檔，使用者不需要另外準備。

## 結構

| 路徑 | 說明 |
|---|---|
| `src/App.tsx` | 外殼：章節列、頁籤列、主題、Ctrl+K，依位址決定渲染哪一章 |
| `src/api.ts` | Rust 指令的型別化包裝。型別必須與 `src-tauri/src/db/` 同步 |
| `src/nav.ts` | 位址模型 `{chapter, tab, anchor}`、章節記憶、捲動與高亮 |
| `src/theme.css` | 兩套主題的 CSS 變數 |
| `src/layout.css` | 版面與元件樣式 |
| `src/chapters/` | 各章節元件，彼此不互相引用 |
| `src/components/` | 卡片、右側小目錄、Ctrl+K、主題切換 |
| `src-tauri/src/db/` | 資料讀取層與資料契約（依章節拆成子模組） |
| `src-tauri/src/lib.rs` | Tauri 指令註冊與啟動流程 |
| `scripts/sync-db.mjs` | 從 `dist/` 同步資料庫 |

## 設計決定

**資料庫唯讀。** Phase 3 之後要加的編輯功能是改 `data/errata` 底下的 YAML
再重建資料庫，而不是直接寫 `.db` —— 直接改會讓修改失去可追溯性，也違背
「SQLite 是建置產物」這個前提。

**介面長得像那本書，而不是像它背後的資料庫。** 原始試算表本來就是分章的，
使用者腦中的模型是「翻到法師那一章」而不是「對全書下篩選條件」。因此是
兩層章節導覽加上一篇篇往下捲的內容，不是一份可篩選的清單。

**搜尋是導覽工具，不是另一種閱讀模式。** Ctrl+K 的每筆結果都帶
`{chapter, tab}` 位址，選中後切章、捲動、高亮，而不是開一個獨立的結果頁。
比對同時涵蓋名稱與效果內文 —— 規則書的效果敘述往往才是玩家記得的那一句
（「每輪回復1d10hp」），只比對名稱等於少掉一半的用處。

**前置鏈是雙向的，而且帶得出位址。** 除了列出這個專長需要什麼，也列出
「把它當前置的其他專長」——「我點了這個之後能開出什麼」是建卡時最常問的
問題。前置可能跨章（職業專長的前置常是一般專長），所以查詢時一併帶回章節
與頁籤，前端不必為了跳轉再往返一次。

**卡片上不放 CP 成本表與勘誤。** `2^等級 × 難度` 是全書通則而非每條專長各自
的性質，印在每張卡上等於把同一條公式重複 612 次；勘誤則是給規則書作者對帳
用的，不是玩家讀規則時要看的東西。兩者各自有獨立的去處。

**主題只換變數值。** 亮暗兩套共用同一組色相，元件的 CSS 一律引用
`theme.css` 的變數、不寫死色碼。唯一分開設計的是難度徽章與強調色 ——
金色在亮底上對比不足、朱紅在深底上會沉掉。

**資料庫找不到時讓啟動直接失敗。** 並印出找過哪些路徑，比開起一個每次查詢
都報錯的空視窗容易診斷。
